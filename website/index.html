neoCLR brings together a managed runtime, application APIs, Raven language integration and developer tools for building and running programs. These parts evolve together through small, executable applications.

The project evaluates changes to .NET-style runtime and library contracts, including generic Void, typed outcomes, UTF-8 text and invariant arrays. Preview 9 is the published baseline; development examples and proposals are labeled separately.

01 — PLATFORM MODEL

Relationship to .NET and the CLI

neoCLR uses CLI concepts for types, methods, assemblies and managed execution. It has its own runtime and library contracts. The current importer admits a bounded subset of CLI artifacts; this does not establish compatibility with arbitrary .NET assemblies.

VALUE & REFERENCE TYPES

Values are copied. Classes and arrays share identity through references. A garbage collector manages heap memory automatically; managed byrefs provide explicit access to storage.

03 — TYPE SYSTEM

Type system: Void in generic APIs

Void has one logical value and can be used as a type argument. That lets the same generic API represent a useful result or completion without a payload.

Func<T, void> expresses a callback with no useful result. neoCLR uses one Func family, including Func<Void> and Func<T, Void>, where .NET uses Action. Result<Void, E> similarly represents completion or a recoverable error.

The Raven sample spells the unit type System.Void. Ordinary void-returning calls still leave no result on the IL stack; the compiler bridges the unit-value contexts.

05 — COMPATIBILITY

Source compatibility and migration

CLI metadata and value/reference concepts provide a shared starting point. Programs still require adaptation to neoCLR’s supported instructions, type contracts and library surface.

Adapt code where outcomes change: null/default checks become Option cases, recoverable exceptions become Result, and Action callbacks become Func with Void. Mutable array covariance also needs adaptation. The preview supports a bounded importer, not unchanged .NET applications.

06 — TOOLING

Raven and VS Code tooling

Raven is the first language integrated with neoCLR. Its compiler emits CLI artifacts; the neoCLR bridge imports the supported subset. Target-specific policies remain separate from Raven’s ordinary .NET target.

neoCLR itself and programs running on neoCLR do not depend on .NET. The surrounding build tools and Raven Language Server run on .NET; the VS Code extension uses that server for editor features.

07 — PLATFORM ROADMAP

Foundations, then an HTTP application pair

The active milestone is a minimal Raven HTTP client and server running on neoCLR. They should exchange UTF-8 text and a small JSON document using shared stream and socket APIs. The runtime and buffer primitives are being tested first through smaller programs.

Memory byte copy, chunked UTF-8 decoding and bounded JSON experiments run today. A controlled delayed-copy sample now exercises real VM completion dispatch, Raven await and GC retention. These are development checkpoints; general stream APIs, sockets and HTTP remain unimplemented.

Preview 9: async and Tasks

Preview 9 packages Task/Promise, await, composition, producer cancellation and isolated workers. Fresh extracted bundles pass the sample and editor checks; source validation covers Linux, macOS and Windows. HTTP and the experimental nonblocking worker adapter remain later work.

Current work: lifetimes and completion

The delayed-copy experiment retains pending receivers through collection and delivers worker results through the default TaskQueue. Completion now progresses between callbacks even while they repost work. Successful worker text/output payloads now have a default 1 MiB limit per worker. Host cancellation now has controlled completion and output-delivery checks. Guest operation cancellation, queue affinity and broader host-memory accounting need further validation before this becomes a general I/O mechanism.

Task implementation and limits →

Next application cases

Streams, Storage and Encoding are next. A bounded file transformer should reuse the byte, text and JSON work. TCP echo follows, then the HTTP client/server pair with independent interoperability checks. Later candidates include a file catalog, download queue, time-aware report, assembly explorer and portable samples; their scope and order remain provisional.

API proposals and implementation status

Explore the proposal overview and open questions →

The following designs are inputs to the roadmap. Their listed status distinguishes working subsets from unimplemented proposals; the list does not commit them to a release.

Unicode text

String represents Unicode text with UTF-8 storage. Char represents a grapheme cluster, while explicit APIs expose scalars and bytes. These units differ from .NET’s UTF-16 Char and require explicit offset conversions at interoperability boundaries.

Status: Grapheme Char, String length and iteration, scalar access and strict UTF-8 conversion work. Normalization, efficient traversal and text positions remain open.

Text proposal →

Time with explicit meaning

Separate Instant and Duration from civil dates, calendar periods and time zones. An injected Clock makes time-dependent code testable; zone mapping exposes ambiguous and skipped local times.

Status: Initial Clock, Instant and Duration APIs are included, with their contracts or value implementations authored in Raven. System.Time migration, zones and periods are planned.

Time proposal →

Culture as immutable data

Separate CultureId, resolved Culture and contextual CultureProvider. Explicit cultures support predictable formatting and testing; an ambient facade keeps ordinary calls convenient. Data versions and fallback still need contracts.

Status: Globalization APIs are proposed. Localization remains a separate future domain.

Globalization proposal →

Async completion and typed errors

Task<T> represents asynchronous completion; Result<T, E> carries expected failures. Await yields the value, and ? propagates a Result error. Task<Void> covers completion without a payload.

Status: Task/Promise, await, composition and explicit producer cancellation are included in Preview 9. Runtime suspension, cancellation tokens and I/O ownership remain open.

Async proposal →

Introspection, reflection and emit

Propose one System.Introspection model of Info interfaces without I-prefixes or public Type/TypeInfo pairs. V1 is runtime-backed through System.Runtime.RuntimeContext. Reflection binds and executes against that context; sibling Emit constructs code without implicitly loading it.

Status: The library has eight sealed Info interfaces, direct TypeInfo acquisition, executing-assembly discovery, module-scoped tokens and Sequence results. Discovery covers retained loaded metadata. Dynamic loading belongs to future RuntimeContext work; invocation, emit and offline contexts remain deferred.

Introspection proposal →

Filesystem contexts

Resolve pure Path values through a FileSystem capability and obtain files and directories from that context. Host and memory implementations can serve the same consumer, with explicit authority and resource lifetime contracts.

Status: Bounded static file helpers exist. FileSystem and its context-bound objects are proposed.

Filesystem proposal →

Streams with precise capabilities

Compose reading, writing, seeking and sizing interfaces, with separate async capabilities. Keep buffering explicit and text decoding above byte I/O. More interface types buy clearer requirements for consumers and decorators.

Status: Stream interfaces, buffer lifetimes and async I/O remain proposed.

Stream proposal →

10 — FEEDBACK & DISCUSSION

Contributing and discussing the design

neoCLR is an early open-source project. Contributions can start with running a sample, asking a question, correcting documentation or reporting a missing API. Compiler, runtime and library changes are also welcome.

For a bug report, include a small program, the toolchain version and expected versus observed behavior when possible. For a design idea, describe the application that needs it and the relevant .NET behavior. A question or counterexample is useful even without a proposed implementation.

The current roadmap keeps work focused on primitives and small executable samples before networking. It is a working plan, and API designs remain open to discussion. For larger changes, open an issue to discuss scope before investing in an implementation.

Influences

.NET/CLR inspires the runtime model and familiar API concepts. Rust’s Result/Option model is a useful precedent for typed outcomes. Raven brings the language and tooling; projects such as Noda Time inform ongoing API research. Research process details →

Current limitations

This is a proof of concept, not a production runtime or a drop-in .NET replacement. The Raven importer supports bounded application classes, interfaces, inheritance and lambda captures. Generic application hierarchies, unrestricted reflection, nullable value types and cleanup during terminal faults remain outside its current scope. The dedicated neoCLR tasks provide build/run; the normal Raven toolbar does not implement this target.

The earlier Neo concept language is preserved as development history. Raven is the language used for the current integration.
