01 — THE APPROACH

Build on what works.
Revisit what could work better.

neoCLR starts from the CLR model. Differences need a purpose, with their costs and limits made explicit.

01

Familiar where it matters

Classes and arrays use reference semantics. Values are copied. Garbage collection manages heap memory. Managed byrefs and native pointers serve their own, explicit purposes.

02

Outcomes in the contract

Result<T, E> represents recoverable errors. Option<T> represents absence. Terminal runtime faults are separate from those ordinary outcomes.

03

A language puts it to the test

An experimental Raven target compiles against neoCLR’s library. It tests the platform through real source programs, with completion and hover in VS Code.

Know the boundaries

This is a proof of concept, not a production runtime or a drop-in .NET replacement. The Raven importer does not yet support arbitrary application hierarchies, capturing closures, unrestricted reflection, nullable metadata or cleanup during terminal faults. The dedicated neoCLR tasks provide build/run; the normal Raven toolbar does not implement this target.

The earlier Neo concept language is preserved as development history. Raven is the language used for the current integration.
